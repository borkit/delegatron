Why it exists, and why it's open.

Delegatron started in April 2026 with one question: could ordinary local models — the kind that fit on a single gaming GPU — write code you could actually rely on, if they had to check each other's work?

A single model asked to write code will cheerfully say it's done. So Delegatron splits the job the way a small team would. An architect writes the plan and the acceptance criteria. An implementer writes the code. A sandbox runs the tests — the one opinion nobody can argue with. A reviewer reads the change and the evidence, then decides. When something fails, the loop goes around again with a clean slate and the failure in hand.

Most of it was built in one intense month by a single developer at StoriaBrevi, much of it pair-programmed with an AI coding assistant — which felt right for a tool about delegating work to AI. It was revisited in the autumn to bring it up to date with newer models.

It began as a possible product. In the end we decided it's more useful as an open, readable example of how a careful multi-agent pipeline fits together: the state machine, the evidence rules, the sandboxing and the budget limits. So it's published under the AGPL-3.0 — anyone can read it, run it and learn from it, and anything built on it as a network service has to stay open too.

It can

  • Write new modules, services, CLI tools and their tests from a description
  • Run entirely on local models through Ollama, on cloud APIs, or a mix per role
  • Test every patch in Docker for six languages
  • Review an existing repository or log files, read-only
  • Split a larger project into milestones and run them in order
  • Resume, retry or refine a run, and open a GitHub pull request when one is approved

It can't

  • Reliably fix bugs in large existing codebases — tools with long exploration loops are better at that
  • Explore open-endedly; it works in a few short iterations per task by design
  • Guarantee that generated code is correct or secure — a person still has to review it
  • Isolate code safely without Docker or E2B; its local mode runs code directly on your machine
  • Be used as a hosted service — there isn't one

Good for

  • Prototypes, hackathon scaffolding and boilerplate
  • Generating a test suite for code you already have
  • Comparing models on the same task with the built-in benchmark
  • Experiments on networks where code can't leave the building
  • Learning how a multi-agent pipeline is put together
