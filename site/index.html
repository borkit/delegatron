§1 The loop

Four roles, one loop, clear rules.

Ask one model to write code and it will tell you the code works. Delegatron splits the job the way a small team would, and lets the tests settle the arguments.

  1. 01

    Plan

    An architect turns the request into small tasks, each with acceptance criteria and the tests that prove it.

  2. 02

    Build

    An implementer writes the code and its tests as a patch. Nothing touches the project until it's checked.

  3. 03

    Test

    The patch runs in an isolated sandbox. A failing test is the one opinion nobody gets to argue with.

  4. 04

    Review

    A reviewer reads the change and the evidence, then approves it or sends it back with the problems listed.

§3 Findings

Six things we learned the hard way.

From benchmarks of four local models and a cloud baseline, on the same tasks and the same hardware. The full numbers are in the repository's docs.

  1. “3” instead of “Fizz”

    Tests and code disagree more often than either is wrong.

    The most common failure across every model: a correct function, and a test that expects the wrong answer. The loop then “fixes” the code to match the broken test.

  2. 30B 2/5 vs 14B 4/5

    A bigger model didn't do better.

    Qwen3-Coder 30B lost to Qwen2.5-Coder 14B on FizzBuzz and on a FastAPI service, and took up to twice as long. It seemed more inclined to rewrite everything.

  3. 6 iterations < 3

    More iterations meant more regressions.

    Doubling the budget on the chess task made results worse. The first attempt got close (9 of 11 tests); every later one broke something that had worked.

  4. 35 GB in system RAM

    A 12 GB card is a hard wall.

    The 30B model's weights don't fit, so most of them stream over PCIe for every token: about 10 tokens a second instead of 50, and budgets run out before the work is done.

  5. 5 s vs 90 s per passing test

    Local was cheaper per run, not per result.

    Measured per passing test or by time to working code, the cloud baseline won by a wide margin. Running locally buys privacy, not savings.

  6. 0 approvals, first benchmark

    Getting local models to finish at all was the real work.

    In the first benchmark, no local model reached an approval on any task, even when every test passed. Simple tasks pass now, after a long list of fixes to the loop itself.

§4 What's in the box

Careful by design.

Any model, any role
Local models on one 12 GB card, cloud models, or a mix, chosen per role.
Hard limits
Iterations, spend and time are capped by Delegatron itself, never left to the model.
Evidence order
Failing tests beat security checks, which beat reviewer objections, which beat opinions. Repeated disputes get one binding ruling.
Patch checks
Leaked secrets, new dependencies and imports that won't resolve are caught before a patch is accepted.
Zero-cloud report
Every run records each network destination it touched, so you can show nothing left the building.
Languages
Python, JavaScript and TypeScript, Go, Rust, Java and PHP, each tested in its own sandbox.
Templates
Thirty: web APIs, command-line tools, audits and test suites.
Interfaces
Terminal, REST API with live updates, or the dashboard. Every run gets its own branch.

§6 Why it's free

Finished, and given away as it stands.

Delegatron is done. It does what this page says it does and stops where this page says it stops, and the gap between the two is the part we found most worth sharing.

Rather than leave it in a drawer, we're publishing the code and the record together under the AGPL‑3.0, so anyone working on models that check each other can start from our results, and our failures, instead of repeating them.
